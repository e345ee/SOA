# Транзакции

`Transactional.TxType` определяет, начинать ли транзакцию и как присоединяться к существующей. Это не уровень изоляции PostgreSQL.

| Граница | Выбор | Причина |
|---|---|---|
| TicketService, PersonService, TicketStatisticsService | REQUIRED | Одна локальная JTA-транзакция на сервисную операцию. Если транзакция уже есть, вызов присоединяется к ней. |
| PersonService.savePersonEntity | MANDATORY | Вспомогательное создание человека выполняется внутри операции создания человека или билета. Ошибка сохранения билета должна откатить и нового человека. |
| EventCancellationService | NOT_SUPPORTED + UserTransaction | Контейнер не открывает внешнюю транзакцию: сервис сам выполняет begin/commit/rollback для массового удаления. |
| BookingService | NOT_SUPPORTED | Сервис отправляет REST-запросы и не держит локальную JTA-транзакцию во время ожидания сети. |

Для CRUD не выбран REQUIRES_NEW: независимый коммит вложенного создания человека оставил бы запись при ошибке сохранения билета. SUPPORTS для записи допускает вызов без транзакции. NEVER на обычных сервисах запрещал бы законные вложенные вызовы. Для программной транзакции NOT_SUPPORTED позволяет безопасно приостановить возможную внешнюю транзакцию, тогда как NEVER отклонил бы такой вызов.

Отмена: Booking отправляет один POST `/api/v1/tickets/cancel-event/{event-id}`. Ticket начинает UserTransaction и выполняет один `DELETE FROM Ticket WHERE eventId = :eventId`. При отсутствии билетов возвращается 404, при успехе — commit и 204, при ошибке — rollback. Последовательного удаления через REST и частично отменённого набора билетов больше нет.

Изоляция БД — READ COMMITTED. Для одного массового DELETE это достаточный уровень: нет отдельного предварительного чтения списка и нескольких порций удаления; строки, подходящие под команду, изменяются атомарно. REPEATABLE READ не даёт нужного выигрыша для одного оператора. SERIALIZABLE добавил бы конфликты сериализации и необходимость повторов, а не запрет создания билетов после завершения отмены. В PostgreSQL READ UNCOMMITTED работает как READ COMMITTED и не даёт отдельного преимущества.

Отмена удаляет билеты, попавшие в снимок команды. API не хранит состояние «событие отменено» и не запрещает последующее создание билетов для того же eventId; для такого правила понадобилась бы отдельная модель жизненного цикла события.

На VPS у PostgreSQL проверяется `SHOW default_transaction_isolation`, у JDBC-пула SharedPoolA явно устанавливаются `transaction-isolation-level=read-committed` и `is-isolation-level-guaranteed=true`. UserTransaction сам по себе уровень изоляции не задаёт.

Локальная транзакция Booking не может откатить HTTP-вызов другого процесса. Поэтому работа с БД перенесена в первый сервис. Если соединение оборвётся после commit, результат команды может быть неизвестен клиенту; создание распределённой транзакции здесь не заявляется.

Основание: [Jakarta Transactions](https://jakarta.ee/specifications/transactions/2.0/jakarta-transactions-spec-2.0.html), [изоляция PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html).

# SOA frontend

Статический интерфейс на HTML/CSS/JavaScript, без сборки и зависимостей.

- `/tickets/` — билеты: таблица, поиск, фильтры, сортировка вложенных полей, пагинация и CRUD.
- `/persons/` — отдельная страница людей с теми же операциями.
- `/booking/` — продажа со скидкой и отмена события.

`assets/contracts.json` содержит два согласованных OpenAPI-контракта. Формы, числовые ограничения, поля фильтров и параметры Booking используют эти схемы. Все API-запросы идут на тот же origin через `/api/v1`, Booking — через `/api/v1/reservation`. Ни TLS-настройки, ни серверная валидация этим интерфейсом не отключаются.

При создании билета существующий человек выбирается из реального `/persons?page=0&size=100&sort=id`. Есть загрузка следующих страниц, повтор загрузки и проверка принадлежности выбранного ID загруженному списку. Альтернатива — создать нового человека вложенным объектом согласно TicketCreate.oneOf. Одновременно personId и person не отправляются.

Дополнительные ограничения фронта: обязательные непустые поля; int32/int64 без дробной части и переполнения; положительные ID, цена и вес; границы координат из YAML; скидка 0–100; конечные float/double без переполнения и обнуления при слишком малой величине; даты с положительным годом и правильным календарным днём, дата рождения не позже текущей даты в Москве; согласованные границы диапазонов. int64 вне безопасного диапазона JavaScript сохраняются через BigInt и отправляются как JSON-числа без потери точности.

Главная таблица содержит только сортируемые заголовки и строки. Фильтры вынесены в раскрываемый блок, редкие действия — в «Ещё». В каждой строке объекта доступны кнопки «Открыть», «Обновить» и «Удалить». Обновление использует ту же схему и валидацию полей, что и создание; ID существующего объекта сохраняется. Перед обновлением и удалением проверяются тип и диапазон ID, перед удалением требуется подтверждение. Для отмены события и удаления объекта предусмотрено подтверждение.

## Размещение на существующем VPS

Публичный каталог `/var/www/kronva-stat`: `index.html`, `assets/`. Nginx должен возвращать index.html только для точных путей `/tickets/`, `/persons/`, `/booking/`; пути без конечного слеша перенаправляются. API и Swagger обслуживаются существующими location. Для assets применяется Cache-Control: no-cache.

Текущий каталог исходников frontend на VPS указан в `/opt/soa-deploy/frontend-run`. Резервные копии предыдущих файлов находятся в `before/` каталога соответствующего backend-релиза.

## Контракт и проверка

GET-списки по согласованному Swagger поддерживают только page/size. Для сортировки и фильтров таблиц используется POST /tickets/search или /persons/search, включая пустой фильтр при сортировке всех записей.

В форме обновления билета существующий человек выбирается из API и отправляется в поле person с его ID; создание использует personId. При явном выборе нового человека отправляется вложенный объект без ID. Все варианты проходят общую фронтовую валидацию, соответствующую схемам и дополнительным требованиям к датам рождения.

На backend с исправлениями контрактов проверены реальные данные, оба направления сортировки всех полей, фильтры, пагинация и повторные обновления без дублирования людей. В браузере подтверждены выбор существующего человека, отклонение нулевой цены и переход между страницами. Проверочные записи удаляются после завершения проверки. Исходные YAML не меняются.
